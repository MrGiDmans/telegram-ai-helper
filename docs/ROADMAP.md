# Roadmap

Что сознательно не реализовано и почему, плюс что стоит улучшить дальше.

## Голосовой слой (не реализовано)

STT/TTS были выбраны на этапе планирования (`faster-whisper` для
распознавания, `Piper` для синтеза — оба CPU-only, чтобы не спорить с LLM за
VRAM), но не реализованы: изначально это опциональный демо-слой поверх
основной истории (агент + память + tool calling + MCP), не блокер. Текст +
документы через Telegram уже полностью рабочий, протестированный путь —
голос можно добавить отдельным клиентским слоем, не трогая ядро.

## Персистентный checkpointer

Сейчас сессионная история — `MemorySaver` (в оперативной памяти процесса),
не переживает перезапуск сервиса. Осознанный компромисс: "постоянная" память
(факты, документы) и так не зависит от этого. Следующий шаг при
необходимости — `AsyncPostgresSaver` (`langgraph-checkpoint-postgres`) поверх
уже существующей БД, без новой инфраструктуры.

## Дизамбигуация документов — известный предел точности

Двухуровневый поиск (описание документа + содержимое чанков) решает
основной случай, но у `nomic-embed-text` есть измеренный предел на
многозначных словах: например "резюме" (CV vs "сводка/итог") даёт близкие
косинусные расстояния до разных документов даже с явным указанием синонимов
в описании и с правильными Nomic-префиксами (`search_query:`/
`search_document:`, которые `langchain_ollama` сейчас не проставляет
автоматически — `embed_query` буквально равен `embed_documents([text])[0]`).
Однозначные формулировки ("CV", "документ на трудоустройство") находят
нужный документ уверенно. Возможные направления: подбор другой
embedding-модели, гибридный поиск (векторный + по названию файла), или явный
уточняющий вопрos от агента при обнаруженной неоднозначности.

## OCR-фолбэк для документов без текстового слоя

Сейчас `ingest_document`/`analyze_document` берут текст из PDF (`pdfplumber`)
или `.docx` (`python-docx`) напрямую. Отсканированные документы без текстового
слоя (или PDF с полностью раздельным изображением-текстом) дадут пустой
результат. Возможный фолбэк — рендер страницы в изображение + OCR
(Tesseract), если станет реальным сценарием использования.

## Наблюдаемость

Сейчас — логирование ошибок на уровне отдельных тулов (`logger.error`).
Следующий шаг для полноценного observability — структурированный JSON-лог
каждого шага агента (какой тул, какие аргументы, что вернул), опционально
через `on_logging_message`/`on_progress` колбэки `langchain-mcp-adapters` —
инфраструктура для этого уже частично разобрана, не подключена по умолчанию.

## Многопользовательский режим

Данные уже партиционированы по `user_id` (реальный Telegram ID, не
LLM-генерируемый) на уровне схемы БД и MCP-тулов — многопользовательский
сценарий не потребует миграции данных. Не хватает: rate limiting на
пользователя, явного управления доступом/квотами, и проверки, что
`MultiServerMCPClient`/подпроцесс MCP-сервера комфортно работает под
конкурентной нагрузкой нескольких пользователей одновременно (сейчас
проверено только последовательное использование).
